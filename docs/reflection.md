# Reflection

I drew the line between my tools with one rule: if a tool's description needed "and", it was really two tools. `search_arxiv` only reads from arXiv, `save_paper_note` only saves one note, and `build_reading_list` exists because "search a topic and save the top papers" is exactly that kind of "and". To keep the save tool single-purpose, it takes the title as an argument instead of fetching it from arXiv, so it can only fail for input or storage reasons. The orchestration tool reuses the same core functions as the other two instead of calling them over MCP, so all validation lives in one place. Three tools felt right for finding and saving papers, and the reading-list tool saves several model calls. Still, it felt tight: I can't delete or edit a note, and the agent can't read back what it saved. I also learned that clear, non-overlapping tool descriptions matter more than the number of tools: in one run, the lite model sent "find 3 recent papers" to `build_reading_list`.

The hardest problems only showed up in live runs. My mocked tests passed, but searching "Model Context Protocol security" returned Bitcoin and DNS papers, because arXiv treats the words as OR. Joining them with AND fixed it. Gemini was the other challenge. `gemini-flash-latest` allowed only 20 free requests a day, and failed requests seemed to count too, so my retries burned the quota. I switched to flash-lite and stopped retrying daily-limit errors. I also raised the reasoning effort after the lite model gave empty replies and picked the wrong tool. Next, I would add a `delete_note` tool, move storage from JSON to SQLite, and add a tool that fetches and summarizes a paper's PDF.
